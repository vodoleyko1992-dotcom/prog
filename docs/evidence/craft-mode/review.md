# Независимое ревью интеграции режима крафта

## Найдено и передано root

1. **Явная смена саба блокировалась режимом.** `subgo.step()` находился только в `loopMenuJobs`, до которого `loopCraft` не пропускает цикл. При этом `craft.free` запрещает крафт при `rt.subGo`. Команда «Одеть лучшее» на уже активном крафтере приводила к бессрочному ожиданию. Root добавил выполнение явной команды `subgo` в `loopCraft` и регрессию.

2. **Старые задания без actionOwner бессрочно держат craft.free.** В `loopCraft` диспетчер вызывается только при `rt.actionOwner` либо `actions.hasPending()`; последнее означает неизвестную оплату, а не наличие любого маршрута. Для legacy `cfg.craftMode:true` без autoTasks `loopTaskList` вовсе не отменяет маршруты, `taskJobAllowed` возвращает true до анализа key. Получаем зависание при `rt.shop` без urgent, `rt.tbuff` или `rt.invScan`, если actionOwner отсутствует. Такие задания создаются до выдачи владельца, поэтому наличие маршрута без владельца — допустимое штатное промежуточное состояние.

   Строгий список тоже не закрывает весь случай: `autoTasks:['craft','mammon']` сохраняет `rt.mmJob`, а `['craft','petbuff']` — `rt.petBufferTrip`, потому что taskJobAllowed раньше проверяет разрешённую группу услуги. Кнопка выбора craft сохраняет сервисные задачи.

   Точный локальный прогон: `node work/craft-mode/review-legacy-repro.cjs`. Использованы текущие функции `loopTaskList`, `loopCraft`, выражение craft.free из content.js и реальный engine-core.js. Для каждого из пяти случаев три тика дали `taskAllowed:true, dispatch:0, step:3, craftFree:false, jobRemains:true`. Игра и сеть не использовались. Это доказательство конкретной блокировки до исправления; файл читает текущие исходники, поэтому после правки вывод может измениться.

   Рекомендация: нормализовать совместимость dedicated craft и при legacy выборе, отменять автоматические маршруты до входа в режим, сохранять квитанции и явно поставленные manual/urgent команды. Не превращать legacy профиль целиком в строгий список и не решать это безусловным запуском прежних автоматических покупок/баффов.

## Что проверено без обнаруженной ошибки

- `autonomyMode` не образует рекурсии с новыми guards: `epicOn`, `huntOn`, `campEnabled` читают cfg, `fishNow` вызывается снаружи.
- `nextFight` запрещает следующую охоту в craft до и после `dailyServerSync`, текущий обычный бой может завершиться.
- `loopGate` и `loopUrgent` оставляют сервер/вход/капчу/PvP/воскрешение/TvT раньше craft.
- `loopCraft` после `antibotGuard` перепроверяет on, tabOwner и фактический режим.
- Дальнейшие async guards самого крафта находятся в отдельном runtime-модуле; полный его аудит не входит в эту проверку.

## Отдельное ревью MP runtime

На первоначальном runtime-модуле независимо воспроизведены два дефекта (`node work/craft-mode/review-runtime-repro.cjs`, существующий тестовый world harness и реальная фабрика, без сети):

1. Книга показывает сырьё на одну попытку и MP0. До свежего GET /character сырьё уходит, свежая revision101. restoreMp проверяет свежий запас банок/MP, но не сырьё, поэтому расходует банку с revision101. Следующий тик сообщает нехватку Iron, готовых предметов0, банок потрачено1. Нужна проверка ingredients выбранного рецепта по свежей inventory до prepare; требования сырья нужны и для решения о повторе старой revision после reload.
2. При удалении заказа во время ACK первого prepare, до POST, pending сохраняется. Новый заказ получает бессрочное ожидание старого q при прежней revision, хотя запрос в данном вызове достоверно не отправлялся. После трёх тиков по65с posts0, pending старого q сохраняется. На этом известном пути отмены можно снять своё sameMp+owner намерение. Неизвестный уже отправленный исход снимать по отмене очереди нельзя.

Root сообщил, что исправляет оба случая и отдельно сохраняет известные settlement-записи при смене режима. Эти исправления ещё не перепроверены данным ревьюером на момент записи. Других доказанных блокеров в просмотренных runtime-путях не найдено; active mode fences подготовки/отправки, fresh revision, Stop/owner guards и разделение нехватки MP/сырья сохранены.

## Финальная перепроверка после исправлений, 22.10.2026

Повторно просмотрены актуальные root `modules/craft.js`, `content.js`, `engine-core.js` и новые регрессии. Найденные выше блокировки и лишний расход закрыты:

- `taskJobAllowed` обрабатывает dedicated craft до legacy-null и разрешённых групп услуг; `loopTaskList` чистит несовместимые маршруты также при legacy выборе. Повтор независимого репро для shop/tbuff/invScan/mmJob/petBufferTrip: все пять записей сняты, `craftFree:true`, старые услуги не исполнялись.
- Явные команды меню и `subGo` обслуживаются dedicated веткой, после них она завершает тик и повторяет guards на следующем круге.
- `mpInputs` сверяет требуемое сырьё со свежим полным персонажем до подготовки банки; requirements сохраняются в pending и проверяются перед same-revision retry.
- При снятом во время первого prepare заказе очищается только своё намерение с тем же ID и владельцем. Неизвестный уже отправленный исход остаётся pending.
- Запись вычисленного результата больше не теряется только из-за изменения mode без смены поколения; `active(t)` сохраняет отдельную строгую проверку mode для расхода.

Независимо выполнено: `node --test tests/craft-mode-runtime.test.js tests/craft-mode-dispatch.test.js tests/craft-mode-ui.test.js tests/v2046-craft-reload.test.js` — **98 PASS, 0 FAIL**. Официальная регрессия дополнительно подтверждает выполнение нового заказа после этой отмены. `git diff --check` — PASS.

Новых доказанных блокеров в финальной просмотренной версии не найдено. Эта проверка локальная: реальные функции и VM/модели сервера, durable-хранилища и отмены.
